# 7.1 Monitoring & Observability

> **Last Updated:** 2026-05-22
> **Related:** [2.5 Cross-Cutting Concerns](../part2_architecture/2.5_cross_cutting.md) · [7.2 Alerting](7.2_alerting.md) · [7.4 Runbooks](7.4_runbooks.md)

---

`agents-council` has no monitoring stack — no metrics endpoint, no dashboards, no log aggregation. Observability comes from three places: the **state file** (the source of truth you can read directly), the **summon debug log** (opt-in), and the **desktop connection indicator**.

## What You Can Observe

| Signal | Where | How to read it |
|--------|-------|----------------|
| Current councils | `~/.agents-council/state.json` | Inspect the JSON; `sessions`, `requests`, `feedback`, `participants` |
| Who has responded | `state.json` feedback authors / participants | Compare participant names to feedback authors per request |
| Pending participants | tool/UI response `pending_participants` | Agents who haven't answered the current request |
| Session status | `state.json` `session.status` + `conclusion` | `active` vs `closed`; conclusion present = sealed |
| Summon lifecycle | `./summon-debug.log` (if enabled) | JSONL: `summon_start` → `summon_session` → `sdk_message` → `summon_success`/`summon_error` |
| MCP server up | stderr | `Council MCP server running on stdio` |
| Desktop connectivity | Hall UI | `connection: "listening" | "offline"` |
| Model Council outcome | tool/CLI result | `consensus.reached`, `ratifiedBy`, `blockedBy`, `converged` |

## Inspecting State

The primary observability action is reading the state file:

```bash
# Pretty-print current council state
cat ~/.agents-council/state.json | jq .

# How many sessions, and which is active?
jq '{active: .activeSessionId, sessions: (.sessions | length)}' ~/.agents-council/state.json

# Feedback authors for the active session
jq -r '.activeSessionId as $s | .feedback[] | select(.sessionId==$s) | "\(.author): \(.content[0:60])"' \
  ~/.agents-council/state.json
```

Because the file is the system of record, this is always accurate — there is no separate metrics store that could drift from reality.

## The Summon Debug Log

When `AGENTS_COUNCIL_SUMMON_DEBUG=1` (or `true`/`yes`), every summon appends structured events to `./summon-debug.log` (in the process CWD):

```jsonl
{"timestamp":"...","event":"summon_start","data":{"agent":"Claude","model":null,"cwd":"..."}}
{"timestamp":"...","event":"summon_session","data":{"sessionId":"...","requestId":"..."}}
{"timestamp":"...","event":"summon_settings","data":{"agent":"Claude","model":null,...}}
{"timestamp":"...","event":"sdk_message","data":{ ...raw SDK message... }}
{"timestamp":"...","event":"summon_success","data":{"feedbackId":"...","feedbackAuthor":"Claude"}}
```

This is the richest diagnostic for summon failures: it shows whether the session/request was found, what model was chosen, every message exchanged with the SDK, and the precise failure (`summon_error` with `message`).

## Desktop Connection Status

The Council Hall reflects connectivity via `useCouncil`'s `connection` field. The desktop bridge / WebSocket subscription transitions it to `offline` on disconnect and `listening` while subscribed. The watcher-driven `state-changed` event causes an immediate re-poll, so a healthy desktop shows new feedback within the 50 ms debounce window of a write.

## Health Checks

| Check | Command | Healthy result |
|-------|---------|----------------|
| CLI installed & versioned | `council --version` | prints a semver |
| CLI help | `council --help` | prints usage |
| MCP server starts | `council mcp` (then Ctrl-C) | `Council MCP server running on stdio` on stderr |
| State readable | `jq . ~/.agents-council/state.json` | valid JSON |
| Summon prerequisites | `claude --version` / `codex --version` | versions print |

These mirror the CI smoke tests (`council --version`, `council --help`).

## Observability Gaps (by design)

| Not available | Implication |
|---------------|-------------|
| Metrics / counters | No quantitative dashboards; inspect the file instead |
| Centralized logs | Each process logs to its own stderr; summon trace is local |
| Tracing | No distributed traces across summon subprocesses |
| Always-on health endpoint | The MCP server is a child process, not a daemon |

For an interactive tool with a single human operator, direct file inspection plus the opt-in debug log is sufficient; heavier observability would be disproportionate.
