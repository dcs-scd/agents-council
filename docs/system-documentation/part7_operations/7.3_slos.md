# 7.3 SLIs, SLOs, SLAs

> **Last Updated:** 2026-05-22
> **Related:** [7.1 Monitoring](7.1_monitoring.md) · [5.1 Infrastructure Architecture](../part5_infrastructure/5.1_infra_architecture.md) · [2.5 Cross-Cutting Concerns](../part2_architecture/2.5_cross_cutting.md)

`agents-council` is a local, single-user, experimental tool with **no formal SLAs**. There is no service to be "up," no uptime contract, and no support tier. This section instead documents the *informal performance expectations* — useful indicators and the latency budget operators can reasonably expect — framed in SLI/SLO language for consistency with the rest of this suite.

## Why There Are No Formal SLOs

- It runs on the user's machine; "availability" equals "the binary runs and the file is readable."
- The MCP server is a child process of the client, not a long-lived service.
- The desktop app is user-launched and exits on last-window-close.
- It is explicitly **experimental**; behavior may change between minor versions.

## Informal Service Level Indicators

| SLI | Definition | Typical |
|-----|------------|---------|
| State read latency | Time for `load()` (read + normalize + verify) | sub-millisecond to a few ms for normal histories |
| State write latency | Time for `update()` under lock | a few ms + lock-acquisition wait |
| Lock acquisition | Time to obtain the `.lock` | immediate when uncontended; up to 10 s under contention |
| Change-to-UI latency | Write → desktop re-render | ~50 ms (watcher debounce) + a poll round-trip |
| Summon latency | `summon_agent` end-to-end | seconds to minutes — bounded by the summoned agent, not the council |
| Model Council latency | `run_model_council` end-to-end | tens of seconds to minutes — bounded by model providers and round count |

The council's own overhead is negligible; nearly all observed latency belongs to the external agents/models it coordinates.

## Implicit "Objectives"

If one were to state objectives for the parts the system *does* control:

| Objective | Target | Mechanism |
|-----------|--------|-----------|
| No torn/corrupt state writes | 100% | Atomic temp+rename |
| No lost writes under concurrency | 100% | File lock + read-modify-write |
| Bounded write blocking | ≤ 10 s | `LOCK_MAX_WAIT_MS`, then throw |
| Self-heal a crashed writer's lock | ≤ 30 s | `LOCK_STALE_MS` reclaim |
| Bounded external probe time | ≤ 8 s | `withTimeout` on model discovery |
| UI freshness after a write | ~1 poll cycle | Watcher event → re-poll |

## Capacity "Limits"

| Dimension | Practical limit | Failure mode at the edge |
|-----------|-----------------|--------------------------|
| Concurrent writers | Dozens polling fine; many simultaneous *writes* serialize | Lock timeout (10 s) under extreme contention |
| Council history size | Tens–hundreds of messages comfortable | Full-file reads slow as history grows very large |
| Sessions retained | Unbounded (no pruning) | Larger `state.json`, slower reads |
| Model Council members | Fixed at 3 | n/a |
| Deliberation rounds | Capped at 4 | Reports `converged: false` if not unified |

## What an Operator Should Promise Themselves

Rather than an SLA, sensible operating expectations:

1. The council will never silently corrupt or lose council state (atomic + locked writes).
2. A blocked write resolves within ~10 s or surfaces a clear timeout error.
3. UI reflects a state change within roughly a poll cycle of the write.
4. Summon and Model Council latency are dominated by the external agents/models — budget accordingly.
5. Cost is incurred only by `run_model_council` / `council solve`.
