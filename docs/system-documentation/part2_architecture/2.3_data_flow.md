## Flow 1 — A Council From Start to Conclusion

The canonical multi-agent flow: one agent starts a council, another joins and replies, the first polls and then closes.

```mermaid
sequenceDiagram
    participant A as Agent A (starter)
    participant MCP as MCP server
    participant SVC as CouncilService
    participant FS as state.json
    participant B as Agent B (joiner)

    A->>MCP: start_council(request, agent_name)
    MCP->>SVC: startCouncil
    SVC->>FS: update() — new session + request + participant
    FS-->>SVC: persisted
    SVC-->>MCP: session_id, assigned agent_name
    MCP-->>A: "Your request is received… name is A"

    Note over B: A shares session_id with B
    B->>MCP: join_council(session_id, agent_name)
    MCP->>SVC: getSessionData
    SVC->>FS: load + record participant
    SVC-->>MCP: request + feedback (empty)
    MCP-->>B: "Welcome… Request: …"

    B->>MCP: send_response(session_id, content)
    MCP->>SVC: sendResponseToSession
    SVC->>FS: update() — append feedback
    MCP-->>B: "Your reply is set down"

    loop poll
        A->>MCP: get_current_session_data(session_id, cursor)
        MCP->>SVC: getSessionData
        SVC->>FS: load + slice feedback after cursor
        SVC-->>MCP: new feedback + next_cursor
        MCP-->>A: messages + cursor
    end

    A->>MCP: close_council(session_id, conclusion)
    MCP->>SVC: closeSession
    SVC->>FS: update() — seal conclusion, close request
    MCP-->>A: "The council is ended"
```

### Key data transformations
- **start_council** writes a `CouncilSession` (`active`), a `CouncilRequest` (`open`), and a `CouncilParticipant`; sets `activeSessionId`.
- **send_response** appends a `CouncilFeedback` row referencing the session's `currentRequestId`.
- **get_current_session_data** returns only feedback *after* the supplied cursor; `next_cursor` is the last returned feedback's id.
- **close_council** sets session `status="closed"`, attaches the `CouncilConclusion`, marks the request `closed`, and re-resolves `activeSessionId` to another active session if one exists.

## Flow 2 — Summon Claude

```mermaid
sequenceDiagram
    participant U as Caller (UI / MCP)
    participant SM as summonClaudeAgent
    participant CFG as config.json
    participant ASDK as Claude Agent SDK
    participant CT as in-proc council MCP
    participant SVC as CouncilService
    participant FS as state.json

    U->>SM: summon_agent(agent=Claude, model?)
    SM->>FS: load — require active session + open request
    SM->>FS: mark participant pending
    SM->>CFG: load + upsert (lastUsedAgent, model)
    SM->>CT: build council tools (scoped to session)
    SM->>ASDK: query(prompt, mcpServers={council}, canUseTool policy)
    ASDK->>CT: join_council
    CT->>SVC: getSessionData
    ASDK->>CT: send_response(content)
    CT->>SVC: sendResponseToSession → append feedback
    ASDK-->>SM: result message
    SM->>FS: load — find the new feedback authored by Claude
    SM-->>U: { agent, model, feedback }
```

The summoned Claude **never gets write access to the project**: `canUseTool` allows only `mcp__council__*` tools plus read-only `Read`/`Glob`/`Grep`; all other tools are denied.

## Flow 3 — Summon Codex

Codex summon is simpler — there is no injected MCP server; the runner submits the feedback on the agent's behalf.

```mermaid
sequenceDiagram
    participant U as Caller
    participant SM as summonCodexAgent
    participant CSDK as Codex SDK (read-only)
    participant SVC as CouncilService
    participant FS as state.json

    U->>SM: summon_agent(agent=Codex, model?, reasoningEffort?)
    SM->>FS: load — require active session + request
    SM->>FS: mark participant pending
    SM->>CSDK: startThread(read-only, no network) + run(prompt)
    CSDK-->>SM: finalResponse text
    SM->>SVC: sendResponseToSession(author=Codex, content=finalResponse)
    SVC->>FS: update() — append feedback
    SM-->>U: { agent, model, feedback }
```

## Flow 4 — Model Council (chair-free consensus)

```mermaid
graph TD
    START([run_model_council / council solve]) --> CFG{OPENROUTER_API_KEY set?}
    CFG -->|No| ERR[Throw: key required]
    CFG -->|Yes| PROP[Propose: all 3 members answer in parallel]
    PROP --> R1[Deliberation round i ≤ 4]
    R1 --> PARSE[Each member returns CANDIDATE_CONSENSUS:]
    PARSE --> UNIFY{All candidates identical?}
    UNIFY -->|Yes| CONVCHECK{Candidate unchanged<br>vs previous round?}
    UNIFY -->|No| MERGE[Candidate = labeled peer drafts]
    MERGE --> CONVCHECK
    CONVCHECK -->|No, rounds left| R1
    CONVCHECK -->|Yes, non-empty| CONVERGED[converged = true]
    CONVCHECK -->|Rounds exhausted| NOTCONV[converged = false]
    CONVERGED --> RAT[Ratify: each member emits CONSENSUS: ACCEPT/BLOCK]
    RAT --> RESULT{All ACCEPT?}
    RESULT -->|Yes| REACHED[consensus.reached = true]
    RESULT -->|No| BLOCKED[reached = false, blockedBy listed]
    NOTCONV --> SKIP[Ratification skipped, all blocked]
```

## Flow 5 — Live Desktop Updates (event-driven)

Unlike polling agents, the desktop re-syncs on file change.

```mermaid
sequenceDiagram
    participant FS as state.json
    participant W as watcher (fs.watch)
    participant BUN as desktop bun process
    participant WV as webview (React)
    participant SVC as CouncilService

    Note over FS: any process writes state
    FS-->>W: fs change event (debounced 50ms)
    W->>BUN: onChange()
    BUN->>WV: rpc.stateChanged({type:"state-changed"})
    WV->>BUN: getCurrentSessionData + listSessions (RPC)
    BUN->>SVC: getCurrentSessionData / listSessions
    SVC-->>WV: fresh snapshot
    WV-->>WV: re-render Hall
```

The same pattern drives the HTTP face, except the watcher `publish`es the `state-changed` event over a WebSocket and the React app re-polls via `fetch`.
