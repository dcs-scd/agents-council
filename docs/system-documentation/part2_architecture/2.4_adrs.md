## ADR-01 — MCP over stdio as the core transport

**Status:** Accepted (v0.1)

**Context.** Agents need to talk to a shared coordination point. The host agents (Claude Code, Codex, Gemini CLI) are all MCP clients.

**Decision.** Expose the council as an **MCP server over stdio**, registered with `npx agents-council@latest mcp`.

**Alternatives considered.** A long-running HTTP server (needs a port, lifecycle management, discovery); a message broker (heavy infrastructure).

**Consequences.**
- ✅ Zero install (`npx`/`bunx`), zero port binding, direct child-process integration with each client.
- ✅ Each client manages the server's lifecycle automatically.
- ⚠️ No push: agents must **poll** for new feedback (mitigated by cursors).
- ⚠️ Each client gets its own server process; coordination must therefore happen through shared *state*, not shared *memory* — see ADR-02.

## ADR-02 — File-based JSON state, not a database

**Status:** Accepted (v0.1)

**Context.** Multiple independent processes (one per MCP client, plus the desktop and any summoned agent) must share one view of a council.

**Decision.** Persist everything to a single JSON file, `~/.agents-council/state.json`, with summon config in a sibling `config.json`.

**Alternatives considered.** SQLite (a dependency, schema migrations, less inspectable); an in-memory server (requires a always-on process and IPC).

**Consequences.**
- ✅ No dependencies, fully portable, trivially inspectable and editable by a human.
- ✅ The file *is* the message bus between processes.
- ⚠️ Requires explicit concurrency control — see ADR-03.
- ⚠️ Not suited to high write rates or very large histories (acceptable for a coordination tool).

## ADR-03 — Lockfile + atomic write for concurrency

**Status:** Accepted (v0.1)

**Context.** Several processes may write `state.json` at once.

**Decision.** Wrap every mutation in `withFileLock`: create a `state.json.lock` with `wx` (exclusive create); on contention, retry every 50 ms up to 10 s; reclaim a lock older than 30 s as stale. Writes go to a uniquely-named temp file, `fsync`, then `rename` over the target (atomic on POSIX).

**Alternatives considered.** OS advisory locks (less portable); last-writer-wins (data loss); a single writer process (reintroduces a server).

**Consequences.**
- ✅ Safe read-modify-write across processes without a server.
- ✅ Crash-safety: a partial write never replaces a good file (temp + rename).
- ⚠️ A crashed writer can leave a `.lock`; the 30 s staleness window self-heals it.

## ADR-04 — Electrobun desktop replaces the HTTP/browser UI

**Status:** Accepted (Milestone 4 / Electrobun pivot)

**Context.** The v0.2 chat UI ran in a browser pointed at a local `Bun.serve` HTTP server. This required port management and a browser tab, and blurred the "is this an app or a server?" line.

**Decision.** Make the **Electrobun desktop app the default face**. `council` with no args launches it; `council chat` becomes a compatibility alias. The renderer talks to the bun core via an Electrobun **RPC bridge** rather than HTTP.

**Alternatives considered.** Electron (much heavier); Tauri (Rust toolchain); keep the browser UI (worse UX, port friction).

**Consequences.**
- ✅ A real, installable, cross-platform desktop app sharing the exact `actions` layer with the old HTTP face.
- ✅ No port for the human UI; native window lifecycle.
- ⚠️ Two parallel UI transports now exist (RPC + the retained HTTP server) — see [Appendix E](../appendices/E_tech_debt.md).
- ⚠️ Packaging complexity: per-platform desktop artifacts (see [5.2](../part5_infrastructure/5.2_deployment.md)).

## ADR-05 — Multi-session state model (v2) with explicit session_id

**Status:** Accepted (Milestone 4)

**Context.** v1 state held a single implicit session. As soon as the desktop showed history and parallel work became plausible, the implicit "current session" was ambiguous.

**Decision.** Move to a **multi-session** state schema: `sessions[]`, `requests[]`, `feedback[]`, `participants[]` keyed by `sessionId`, plus an `activeSessionId`. Every MCP tool and bridge action takes an explicit `session_id`.

**Alternatives considered.** Keep one session and reset between councils (loses history); separate files per session (complicates the watcher and active-session logic).

**Consequences.**
- ✅ Parallel councils, replayable history, an unambiguous target for every operation.
- ✅ A clean migration path from v1 (see ADR + [3.5](../part3_data/3.5_migrations.md)).
- ⚠️ Tools gained a required `session_id` argument; clients must thread it through.

## ADR-06 — Server-assigned agent names with #N suffixing

**Status:** Accepted (early; replaced opaque agent ids)

**Context.** Agents self-declare a human-friendly name, but two agents may pick the same one.

**Decision.** The server resolves names: if `Name` is taken in a session, return `Name#1`, `Name#2`, …. The resolved name is echoed back and must be reused. A startup default (`-n`) removes the per-call `agent_name` argument.

**Consequences.**
- ✅ Friendly, collision-free identities with no coordination.
- ✅ Idempotent reuse: an existing participant name is reused rather than re-suffixed (`allowReuse`).
- ⚠️ Names are not authenticated — identity is advisory only (see [6.1](../part6_security/6.1_security_architecture.md)).

## ADR-07 — Read-only summon sandbox

**Status:** Accepted (v0.3 / v0.4)

**Context.** A summoned agent should *advise*, not change the user's project.

**Decision.** Constrain summoned agents to read-only. Claude summon's `canUseTool` allows only the council tools plus `Read`/`Glob`/`Grep` and denies everything else; Codex summon runs with `sandboxMode: "read-only"`, `approvalPolicy: "never"`, `networkAccessEnabled: false`, `webSearchEnabled: false`.

**Consequences.**
- ✅ A summoned agent can ground its advice in the codebase but cannot mutate files or reach the network.
- ✅ Reuses the human's existing CLI auth without granting write scope.
- ⚠️ A summoned agent that *needs* to run something cannot; it can only reason from what it reads.

## ADR-08 — Chair-free, peer-ratified consensus in the Model Council

**Status:** Accepted (current)

**Context.** A naive "ask three models and have one summarize" makes the summarizer the de-facto decider.

**Decision.** No chair. Members propose independently, deliberate over up to four rounds emitting an explicit `CANDIDATE_CONSENSUS:` block, and — only once the candidate converges — each **independently** emits `CONSENSUS: ACCEPT` or `CONSENSUS: BLOCK`. Consensus is *reached* only if **every** member ratifies.

**Alternatives considered.** Majority vote (a 2-1 split still overrides a valid objection); a designated synthesizer (chair bias).

**Consequences.**
- ✅ A single dissenting peer can block, preserving correctness over agreement.
- ✅ The result reports `ratifiedBy` / `blockedBy` transparently; "no single agent decided the result."
- ⚠️ Consensus may not be reached; the system reports a blocked outcome rather than forcing one.
- ⚠️ Up to `members × (1 + rounds + 1)` model calls per run — a real cost (see [5.3](../part5_infrastructure/5.3_environments.md)).

## ADR-09 — Shared, face-agnostic action layer

**Status:** Accepted (Electrobun pivot)

**Context.** The desktop (RPC) and the HTTP server should not duplicate logic.

**Decision.** Put all request validation + service orchestration in `interfaces/chat/bridge/actions.ts`. The HTTP server and the Electrobun RPC handlers both delegate to the same action functions; errors are normalized as `BridgeApiError(status, message)`.

**Consequences.**
- ✅ One implementation of each operation across two transports.
- ✅ The MCP face reuses the same DTO `mapper` as the bridge.
- ⚠️ Minor divergence: MCP threads `session_id` explicitly while bridge actions operate on the active session for some calls — a deliberate ergonomic split.
