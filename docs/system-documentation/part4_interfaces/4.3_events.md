> **Related:** [4.2 Internal APIs](4.2_internal_apis.md) · [2.3 Data Flow](../part2_architecture/2.3_data_flow.md) · [Appendix B: Schemas](../appendices/B_schemas.md)

This is the wire contract reference: the MCP tools agents call, the HTTP endpoints and Electrobun RPC the UIs call, the JSON-RPC the Codex `app-server` speaks, and the single `state-changed` event.

## MCP Tools

The MCP server (`council mcp`) registers seven tools. All take strict (`.strict()`) Zod-validated objects. Results carry both a human-readable `text` block (markdown or JSON, per `--format`) and a `structuredContent` payload.

### `start_council`
Open a new session and post the first request.

| Param | Type | Notes |
|-------|------|-------|
| `request` | string (min 1) | The matter to discuss |
| `agent_name` | string (min 1) | Required **unless** the server started with `-n <name>` |

Returns `{ agent_name, session_id, request_id, state }`. The server may append `#N` to the name.

### `join_council`
Join an existing session and fetch its request + responses.

| Param | Type | Notes |
|-------|------|-------|
| `session_id` | string (min 1) | Required |
| `agent_name` | string (min 1) | Required unless `-n` set |

Returns a `GetCurrentSessionDataResponse`.

### `get_current_session_data`
Poll a session for new responses.

| Param | Type | Notes |
|-------|------|-------|
| `session_id` | string (min 1) | Required |
| `cursor` | string (min 1) | Optional; last-seen feedback id |

Returns `{ agent_name, session_id, request, feedback[], participant, next_cursor, pending_participants[], state }`. Requires a stored agent name (call `join_council`/`start_council` first).

### `send_response`
Submit feedback to a session.

| Param | Type | Notes |
|-------|------|-------|
| `session_id` | string (min 1) | Required |
| `content` | string (min 1) | The response |

### `close_council`
End a session with a conclusion.

| Param | Type | Notes |
|-------|------|-------|
| `session_id` | string (min 1) | Required |
| `conclusion` | string (min 1) | The sealed summary |

### `summon_agent`
Summon a fresh Claude or Codex into the active session.

| Param | Type | Notes |
|-------|------|-------|
| `agent` | enum `"Claude" \| "Codex"` | Required |
| `model` | string | Optional; validated against the cached model list for that agent |

Returns `{ agent, model, feedback }`.

### `run_model_council`
Run the chair-free three-agent consensus.

| Param | Type | Notes |
|-------|------|-------|
| `prompt` | string (min 1) | The problem to deliberate |

Returns the full `ModelCouncilResult`.

### Schema adaptivity
When the server starts with `-n <name>`, `start_council` and `join_council` drop `agent_name` (the schema becomes `{request}` / `{session_id}`) and the bound name is used automatically. Tool *descriptions* also adapt, and the `summon_agent` description embeds the available models when a cache exists.

### Server instructions
On connect, the MCP server advertises usage guidance, e.g.:
> "If you need feedback from other AI agents, start a council with start_council." … "Use get_current_session_data with session_id to poll for new responses; pass the cursor returned to fetch only newer messages." … "Use run_model_council when the user wants Kimi 2.6, DeepSeek V4 Pro, and ChatGPT 5.5 Pro to deliberate and reach peer-ratified consensus without a chair."

## In-Process Council Tools (Summon Claude)

When Claude is summoned, an in-process MCP server named `council` exposes three scoped tools to that agent (no `session_id` — it is bound to the active session):

| Tool | Args | Purpose |
|------|------|---------|
| `join_council` | (none) | Fetch the session request + responses |
| `get_current_session_data` | `cursor?` | Fetch responses since a cursor |
| `send_response` | `content` | Submit the agent's single response |

These appear to the summoned agent as `mcp__council__join_council`, etc., and are the only non-read tools its `canUseTool` policy permits.

## HTTP Endpoints (chat server / alt face)

`Bun.serve` (`interfaces/chat/server.ts`) exposes the bridge actions over HTTP. All are `POST` with a JSON body; responses are JSON.

| Path | Action |
|------|--------|
| `/start-council` | startCouncilAction |
| `/join-council` | joinCouncilAction |
| `/get-current-session-data` | getCurrentSessionDataAction |
| `/list-sessions` | listSessionsAction |
| `/set-active-session` | setActiveSessionAction |
| `/send-response` | sendResponseAction |
| `/close-council` | closeCouncilAction |
| `/get-summon-settings` | getSummonSettingsAction |
| `/refresh-summon-models` | refreshSummonModelsAction |
| `/update-summon-settings` | updateSummonSettingsAction |
| `/summon-agent` | summonAgentAction |
| `/get-settings` | getSettingsAction |
| `/update-settings` | updateSettingsAction |
| `GET /` | serves the React UI |
| `GET /ws` | WebSocket upgrade for state-changed events |

Errors return `{ error }` with the mapped status (`BridgeApiError.status` or 500; `EADDRINUSE` → friendly port message).

## Electrobun RPC Contract

The desktop renderer talks to the bun process via the `CouncilDesktopBridge` interface (`bridge/contract.ts`), exposed on `window.__COUNCIL_DESKTOP_BRIDGE__`. Each method mirrors an HTTP endpoint but returns a `BridgeResult<T>`:

```typescript
type BridgeResult<T> = { ok: true; data: T } | { ok: false; error: string };
```

Methods: `startCouncil`, `joinCouncil`, `getCurrentSessionData`, `listSessions`, `setActiveSession`, `sendResponse`, `closeCouncil`, `getSummonSettings`, `refreshSummonModels`, `updateSummonSettings`, `summonAgent`, `getSettings`, `updateSettings`, plus `subscribeStateChanged(listener)` returning an unsubscribe function.

The bun process registers these as RPC `requests` handlers (`desktop/bun/index.ts`), each wrapping an action in `runBridgeAction` to produce the `BridgeResult`.

## The `state-changed` Event

The system's only push message:

```typescript
type CouncilStateChangedEvent = { type: "state-changed" };
```

| Face | Delivery |
|------|----------|
| Desktop | `window.webview.rpc.stateChanged(event)` from bun → renderer |
| HTTP | `server.publish("council-state", JSON.stringify({type:"state-changed"}))` over WebSocket |

The event carries **no payload** — it is purely a signal to re-poll `getCurrentSessionData` + `listSessions`. It is emitted by the `fs.watch` watcher (debounced 50 ms) whenever `state.json` changes, regardless of which process wrote it.

## Codex `app-server` JSON-RPC

Used only for Codex model discovery (`fetchCodexModelsViaAppServer`). Newline-delimited JSON-RPC 2.0 over the subprocess's stdio:

```text
→ {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"clientInfo":{...}}}
→ {"jsonrpc":"2.0","method":"initialized","params":{}}
→ {"jsonrpc":"2.0","id":2,"method":"model/list","params":{}}
← {"jsonrpc":"2.0","id":2,"result":{"data":[ ...models... ]}}
```

Bounded by an 8 s timeout; the subprocess is killed afterward.
