# v0.6 Parallel Sessions — Decision Brief

**Status:** Decision input. Adjudicates the "bb patterns" adoption items #2 (store
migration) and #3 (provider/notification contracts). Authored 2026-06-23.

**Audience:** Whoever drives the next v0.6 work — read this *before* writing any
plan or opening a store-migration task.

**TL;DR:** v0.6 parallel sessions is ~90% already built at the data and service
layers. Do **not** migrate to SQLite. The only store concern (single global
file-lock + whole-graph revalidation per write) is **unmeasured** and almost
certainly irrelevant at council pace. Gate any store change behind a contention
benchmark. The genuine remaining v0.6 work is small and lives at the MCP-tool and
desktop-UI layers, not the store. Item #3 is a **KILL** — no consumer exists.

---

## 1. What already exists (verified in code, 2026-06-23)

The state schema is already multi-session (V2): `sessions[]`, plus a `sessionId`
foreign key on every `request`, `feedback`, and `participant`
(`src/core/state/fileStateStore.ts`). Legacy V1 single-session state is migrated
forward automatically (`migrateLegacyCouncilStateV1`).

Every council operation already has a **session-addressed** service method:

| Operation | Session-addressed method | Location |
|---|---|---|
| read    | `getSessionData(sessionId)`            | `core/services/council/index.ts:245` |
| write   | `sendResponseToSession({ sessionId })` | `core/services/council/index.ts:323` |
| close   | `closeSession({ sessionId })`          | `core/services/council/index.ts:154` |
| list    | `listSessions()`                       | `core/services/council/index.ts:228` |
| switch  | `setActiveSession()`                   | `core/services/council/index.ts:276` |
| wait    | `wait_for_session_data` (MCP)          | `interfaces/mcp/sessionDataWait.ts` (added 2026-06-23) |

Conclusion: **the data model and core service already support multiple
coexisting, independently-addressed sessions.** Parallel sessions are not a
greenfield build; they are a finishing job.

## 2. What is actually missing for v0.6

Only two real gaps, both *outside* the store:

1. **MCP-layer convenience tools are still bound to the singular `activeSessionId`.**
   `getCurrentSessionData`, `sendResponse`, and `closeCouncil` resolve via
   `getActiveSession(state)` (index.ts:100, 142, and `sendResponse` →
   `sendResponseToSession({ sessionId: null })` at :220). An agent driving two
   sessions from one MCP client cannot disambiguate through these three tools.
   **Fix (small):** let each accept an optional `session_id` that, when present,
   routes to the already-existing session-addressed method; when absent, keep
   today's active-session behavior. Purely additive, mirrors how
   `wait_for_session_data` was added.

2. **Desktop UI assumes one active session.** `activeSessionId` is singular and
   the Council Hall renders a single active session. True parallel use in the
   GUI needs a session switcher / multi-pane affordance. This is UI work, not
   store work; sequence it per `docs/ui-spec.md`.

## 3. The store question — measurement kill-gate (do NOT skip)

The proposed SQLite migration (#2) targets this property: `withFileLock` keys on
the single global state-file path (`fileStateStore.ts:72,80`), so **every** write
to **any** session serializes on one lock, and each `update()` rewrites the whole
file and re-runs `assertCouncilStateIntegrity` over the entire graph (lines
545–617).

This is **correct** behavior. The only open question is throughput, and it is
**unmeasured**. Before any store change is justified:

**KILL-GATE (measure first):**
- Write a micro-benchmark: N concurrent MCP servers (N ∈ {2, 5, 10, 20}) each
  issuing `send_response` to its own session, sustained for ~60s at a realistic
  inter-write interval (start at 2s — actual council cadence).
- Record: p50 / p99 write latency, lock-wait time, and `assertCouncilStateIntegrity`
  cost as the graph grows (seed 100 / 1k / 5k feedback rows).
- **Gate:** a store change is justified **only if** p99 write latency or lock-wait
  exceeds a stated budget (proposal: p99 lock-wait > 50 ms at N=10, realistic
  cadence). If the gate is not crossed, **STOP — ship v0.6 with §2's MCP+UI work
  only and no store change.** Record the null result.

**If — and only if — the gate is crossed,** prefer the *minimal* fix that
preserves the local-JSON / zero-infra differentiator, in this order:
1. **Per-session lock granularity** — key `withFileLock` on a per-session path so
   writes to distinct sessions don't contend. Smallest change; keeps one JSON
   file or shards to per-session files.
2. **Per-session file sharding** — one JSON file per session + a small index
   file; whole-graph validation becomes per-session validation.
3. **SQLite** — only if 1 and 2 are shown insufficient. This is the heaviest
   option, contradicts `AGENTS.md` ("avoid extra layers… unless proven need"),
   moves the architecture toward bb (the competitor), and carries data-migration
   risk for every existing `~/.agents-council/state.json`. Treat as last resort.

**Recommendation (confidence: high):** the gate will not be crossed at council
pace. Expected outcome is §2 work only, store untouched.

## 4. Item #3 (v0.7/v0.8 provider + notification contracts) — KILL

The earlier "Everything" scope included pre-building provider and notification
abstraction contracts for v0.7 (external LLMs via API keys) and v0.8 (summon user
via Telegram/Slack).

**Recommendation: do not build now (confidence: high).** There is no consumer.
Pre-building abstraction layers for unshipped features is precisely what
`AGENTS.md` prohibits ("avoid extra layers… unless there is an immediate, proven
need") and what `KARPATHY.md` simplicity-first prohibits ("no flexibility or
configurability that wasn't requested"). The existing roster mechanism
(`AGENTS_COUNCIL_MEMBERS` + per-provider model env vars + the OpenRouter path
already in `README.md`) is the proven extension seam; widen it when a real v0.7
provider lands, not before. Revisit only when v0.5 (Summon Gemini) or v0.7 has a
concrete first consumer.
